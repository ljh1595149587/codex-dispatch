# 派活档位、Claude 额度与验收分工（设计）

> 2026-10-26 定稿待确认。实现见 `bin/policy.py`、`hooks/dispatch_hook.py`；本文只讲规则和为什么。

## 0. 要解决的问题

skill 只是说明书：派不派由 Claude 在干活途中自己判断，而那正是它最想「顺手做完」的时候。
实测：2026-09-01 之后所有项目的派活日志零记录（连「考虑过、决定自己做」都没有），派出去的几乎全是审查和探索，开发实现一次没派过。
所以本设计把约束分到三层：**skill 讲怎么做，派活脚本和钩子管必须做，统计让偏离看得见。**

## 1. 档位（level）

| 档位 | 适合 | 实现默认谁做 | Codex 负责 | 强制方式 | 预期 Codex 占比（只作体检） |
|---|---|---|---|---|---|
| 0 关 | 原型、一次性脚本、探索验证 | Claude | 用户明确要求时 | 无 | ≈0 |
| 1 轻 | 可用项目（自用工具，能用就行） | Claude | 读多写少的排查；中风险以上改动的审查 | 第 2 个分析脚本起提醒 | 10~20% |
| 2 中 | 工程项目（有真实用户、长期维护） | 需求写得清、有测试能判对错的活 → Codex；设计、模糊需求、核心逻辑 → Claude | 上述实现 + 补测试 + 审查 Claude 写的中高风险改动 | 阶段须填执行者；Claude 改源码累计到阈值时须写明「派 / 不派 + 理由」 | 30~60% |
| 3 重 | 严格工程，或用户就要 Codex 主写 | Codex；Claude 只写需求、验收标准、测试并验收 | 几乎所有实现 | Claude 直接改源码被拦截；确需小修须先登记理由 | ≥80% |

**占比不是目标，是体检。** 拿占比当目标会把不该派的活硬派出去凑数；规则当目标、占比当体检，连续偏离预期区间说明档位设得不对或 Claude 在跑偏。

## 2. Claude 额度（claude_budget）

只有两档：`ample`（宽裕，如 Max 5x）、`tight`（紧，如 Pro）。Codex 额度视为充足，不建模。

生效档位 = `ample` 时等于项目档位；`tight` 时 **= max(项目档位 + 1, 2)，上限 3**：

| 项目档位 | ample | tight |
|---|---|---|
| 0 | 0 | 2 |
| 1 | 1 | 2 |
| 2 | 2 | 3 |
| 3 | 3 | 3 |

`tight` 额外生效「省 Claude 上下文」规则：排查 / 读日志 / 统计一律派 Codex 只读档、报告 ≤4KB；改→测→修循环归 Codex；验收只看改动统计、关键片段和验收命令输出，深度审查走两轮审查、Claude 只裁决；Claude 只保留沟通、需求与验收标准、决策、最终验收。

## 3. 配置在哪

| 设置 | 位置 | 说明 |
|---|---|---|
| `claude_budget`、`default_level` | 用户级 `~/.claude/codex-dispatch.json` | 跟着订阅走；换套餐改一次 |
| `level`（可选 `source_exts`、`exclude`） | 项目级 `<项目根>/.claude/codex-dispatch.json` | 新项目设一次；提交与否由用户定 |
| 临时覆盖 | `policy.py override --level N`（用户说「这次按 N 档」时由 Claude 执行） | 只对本会话有效，会话结束自动失效 |

优先级：临时覆盖 > 项目级 > 用户级默认。配置写错时带警告回落、不静默乱跑：项目级写错 ⇒ 按**用户级默认档位**（你设了默认 3，不该因某个项目配置写坏就悄悄降到 1）；用户级写错 ⇒ 按内置默认（level 1、ample）。警告会出现在会话开始那一行里。
项目根 = cwd 所在 git 仓库的根；不在 git 仓库里就用 cwd。

## 4. 验收分工

**实现者不能是唯一验收者。** 四层：

| 层 | 内容 | 谁做 |
|---|---|---|
| 1 验收标准 | 动手前写下怎样算完成（测试、命令、期望输出） | 非实现方 |
| 2 客观检查 | 测试、lint、类型检查、构建 | 机器跑，**验收方亲自运行**看原始输出 |
| 3 交叉审查 | diff 对照需求：漏的、多做的、错的 | 另一方 |
| 4 实际环境验证 | 真实环境跑一遍 | Claude，证据给用户 |

- **Codex 实现 → Claude 验收**：Claude 先按需求写验收测试；重点查「多做了」和「改了测试」（受保护路径由派活脚本 `-Protect` 自动判不合格）；只看 `git diff` 和命令输出。
- **Claude 实现 → Codex 验收**：两轮审查，并给针对 Claude 毛病的清单（如「列出 X 的所有调用点逐个确认」）；边界测试由 Codex 按需求写。**Claude 驳回 Codex 的发现必须给证据**（测试或 file:line），驳回条目记进派活日志。
- **分歧**：以客观证据为准（补测试）。只有证据无法判定的设计取舍才拿事实问用户。

风险决定验收深度，与档位无关：低（文档、小修）= 第 2 层；中（一般功能）= 1+2+3（审查一轮）；高（迁移、计费、鉴权、并发、部署）= 四层全做、第 3 层两轮对抗。

## 5. 钩子做什么（全局，写在 ~/.claude/settings.json）

skill 自带的 frontmatter 钩子只在该 skill 被调用过的会话生效，常驻约束必须放用户级 settings。所有钩子出错时**放行**（不让工具链故障卡住正常工作），只有档位 3 的拦截是有意为之。

| 事件 | 做什么 |
|---|---|
| SessionStart | 注入一行生效档位与本档规则摘要；配置无效时说明原因 |
| PreToolUse（Edit/Write/MultiEdit/NotebookEdit） | 档位 3：改项目源码 ⇒ 拒绝，除非已用 `policy.py decide self --reason ...` 登记（豁免 30 分钟或指定文件） |
| PostToolUse（同上 + Bash、PowerShell） | 记 Claude 改动的文件与行数；命令行改文件用 git 快照前后对比发现（见下）；识别分析脚本（内联 python/awk 长程序、在项目外写 .py/.sh）；按档位提醒 |
| Stop | 本轮有改动或派活时，给用户一行统计（阶段字段的完整性由 planning 自己检查） |
| SessionEnd | 会话汇总写入 `~/.claude/codex-dispatch-state/stats.jsonl`；清掉本会话的临时覆盖 |

提醒规则：档位 1、2 在本会话第 2 个分析脚本时提醒，之后每多 3 个再提醒；档位 2 在 Claude 改源码累计 3 个文件或 80 行（自上次登记决定起）时提醒，要求执行 `policy.py decide dispatch|self --reason ...`。

**「源码」**：项目根内、扩展名属于常见代码类型（可在项目配置里改），排除 docs、规划文件、`.claude`、`node_modules`、`dist` 等。

**命令行改文件**：2026-10-26 实测，Claude Code 给 Bash 钩子的结果里**没有**改动文件列表（只有 stdout/stderr 等），在 git 仓库里 `sed -i` 也一样。所以改用 git 快照：会话开始记下有改动的源码文件及修改时间，每条命令后再取一次，不经编辑工具变化的就记为命令行改动。编辑工具改过的文件同步进快照（不重复计）；派活脚本那条命令不归因；后台派活期间（直到派活脚本统计完 Codex 改动）不归因，标记最长 2 小时。

**已知漏洞**：命令行改动拦不住，只能事后记账 + 提醒（档位 3 记为违规）；行数只计文件数；`go generate` 这类生成命令产出的源码也会算作 Claude 的命令行改动（确属 Claude 触发，档位 3 下先登记再跑）。所以档位 3 的「Claude 不碰源码」要靠拦截 + 事后统计一起看。

## 6. 和 planning-with-files-zh 的对接

planning-with-files-zh 是用户自己维护的 skill（不跟随原作者更新）。分工：**格式归 planning，规则归本 skill。**
planning 的 task_plan 模板每个阶段自带四行，缺字段的提醒也由 planning 自己做：

```markdown
- **状态：** pending
- **执行者：** Codex（需求清楚、有测试能判对错）
- **验收者：** Claude
- **风险：** 中
- **验收证据：** （完成时填：命令输出、审查结论的位置）
```

本 skill 只读这些字段：档位 ≥2 时 SessionStart 提醒按字段分工；统计时把阶段的执行者与实际改动对照。
派活与验收记录仍写 `docs/dispatch-log.md`，progress.md 只记一句结论。不用 Codex 的项目（档位 0）照常使用 planning，字段可填「Claude」。

## 7. 统计口径

- Claude：编辑工具的新旧内容行数差（Write 按写入行数计）；命令行改动只计文件数
- Codex：派活脚本写模式跑完后 `git diff --numstat` + 新增未跟踪文件行数（开工前工作树必须干净，所以这就是 Codex 的改动）
- 会话结束一行：`Claude 改 N 文件 +a/-b · 命令行改 k 文件 · Codex 派活 m 次 +c/-d · 生效档位 L`
